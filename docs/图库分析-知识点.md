# 第 10 章 · 图库分析 —— 知识点整理

> 本章代码：`SpaceAnalyzeController` / `SpaceAnalyzeService(Impl)` / `model.dto.space.analyze` / `model.vo.analyze`
> 本文只讲「为什么这么写」，代码细节自己看。

---

## 一、这一章做了什么

6 个分析接口，全部 `POST /space/analyze/*`：

| 接口 | 统计内容 | 关键 SQL / 手段 |
|---|---|---|
| `/usage` | 已用大小、已用数量、两个百分比 | 指定空间读 **space 表**；全空间/公共读 picture 表 |
| `/category` | 每个分类的图片数、总大小 | `GROUP BY category` |
| `/tag` | 每个标签出现多少次 | 取出 tags JSON，**内存里**合并 |
| `/size` | 4 个大小区间的图片数 | 取出 picSize，**一遍遍历**分桶 |
| `/user` | 按日/周/月的上传数量 | `DATE_FORMAT` / `YEARWEEK` |
| `/rank` | 占用存储最多的前 N 个空间 | `ORDER BY totalSize DESC LIMIT n` |

## 二、一个接口服务三种范围（本章最重要的设计）

### 1. 观察：三种范围只差 where

```sql
-- 用户看自己的空间
SELECT category, SUM(picSize) FROM picture WHERE spaceId = 10   GROUP BY category;
-- 管理员看公共图库
SELECT category, SUM(picSize) FROM picture WHERE spaceId IS NULL GROUP BY category;
-- 管理员看全空间
SELECT category, SUM(picSize) FROM picture                               GROUP BY category;
```

统计方式一模一样，只有 where 不同。所以**不要写三个接口**，而是做一个基类
`SpaceAnalyzeRequest { spaceId, queryPublic, queryAll }`，让 5 个具体请求继承它。

于是每个分析需求都只有两段可复用代码：

```java
checkSpaceAnalyzeAuth(req, loginUser);      // 校验
fillAnalyzeQueryWrapper(req, queryWrapper); // 填 where
```

**这就是「面向变化点抽象」：变的是范围和权限，不变的是统计。**

### 2. 优先级：queryAll > queryPublic > spaceId

`fillAnalyzeQueryWrapper` 里 `if / return` 的顺序就是优先级：

1. `queryAll = true` → **不加任何空间条件**
2. `queryPublic = true` → `spaceId IS NULL`
3. `spaceId != null` → `spaceId = ?`
4. 都没有 → 抛 `PARAMS_ERROR "未指定查询范围"`

为什么必须有优先级？因为三个参数同时传时必须有确定的语义，不能"看运气"。
现在的语义是「大范围吃掉小范围」。

> ⚠️ 注意第 4 条：一定不能有"什么都不加"的兜底分支。否则前端漏传参数，
> 普通用户就拿到了**全站数据**——这是分析接口最典型的越权漏洞。

### 3. 公共图库 = `spaceId IS NULL`，不是 `spaceId = 0`

数据库里"没有空间"是用 NULL 表示的，不是 0。
`spaceId = 0` 在 SQL 里永远匹配不到任何行（NULL 参与比较结果是 UNKNOWN），
写错了不会报错，只会**静默返回空结果**——比报错更难查。

### 4. 两条权限路，依据不同

| 范围 | 谁能看 | 授权依据 |
|---|---|---|
| queryAll / queryPublic | 仅管理员 | **角色**（`userService.isAdmin`） |
| spaceId | 空间创建者 或 管理员 | **所有权**（`space.getUserId()`） |

这两条路的依据不一样，所以不能合并成一个判断。
普通用户即使能看到全站图片列表，也不能看别人的空间分析——那是别人的经营数据。

代码里复用了项目已有的 `SpacePermissionHelper.checkSpaceAccess`，它比笔记版多查了一项：
**空间被禁用时普通用户不能访问**（管理员仍可）。

## 三、`/usage`：为什么指定空间不查图片表

`space` 表里有 `totalSize` / `totalCount` 两个冗余字段，上传/删除图片时同步维护。

- **指定空间**：直接 `spaceService.getById()` 一次主键查询，O(1)。
- **全空间 / 公共图库**：没有"总表"可查，只能扫 picture 表。

如果指定空间也去扫 picture 表：一个空间 10 万张图，就要读 10 万行算 SUM。
而 space 表一行就够。

**代价**：冗余字段可能和真实数据不一致（并发上传时漏更新、历史数据迁移）。
这就是"空间配额"这个功能里最经典的坑——第 8 章的批量操作之所以要同时更新
`space.totalSize/totalCount`，就是为了维持这份冗余。

### `selectObjs` 与「只查需要的列」

```java
queryWrapper.select("picSize");
List<Object> list = pictureService.getBaseMapper().selectObjs(queryWrapper);
```

- `select("picSize")` → SQL 只查一列，不查 `url`、`introduction` 这些大字段
- `selectObjs` → 结果**不封装成 `Picture` 对象**，直接给你一列 `Object`

封装实体会走反射 + 创建对象，10 万行就是 10 万个对象。分析场景只要一个数字，没必要。

## 四、`SUM()` 返回的不是 Long（实测）

```java
Long totalSize = ((Number) result.get("totalSize")).longValue();  // 对的
Long totalSize = (Long) result.get("totalSize");                  // 错的，ClassCastException
```

实测（本机 MySQL，`picture.picSize` 是 `bigint`）：

```
columns: [1]category (VARCHAR)  [2]count (BIGINT)  [3]totalSize (DECIMAL)
row1: category=null  count=10<Long>  totalSize=36970448<BigDecimal>
```

原因：**MySQL 的 `SUM()` 对整型列做类型提升，返回 `DECIMAL`**，因为求和可能溢出 BIGINT。
`COUNT(*)` 才是 BIGINT。

所以聚合结果统一用 `Number` 接：

```java
private static Long toLong(Object value) {
    return value instanceof Number ? ((Number) value).longValue() : 0L;
}
```

同理 `YEARWEEK()` 返回 `Integer`（实测），`DATE_FORMAT()` 返回 `String`。
**永远不要假设 JDBC 给你的 Java 类型。**

## 五、标签分析：为什么必须在内存里做

`picture.tags` 存的是 JSON 数组字符串：`["java","mysql"]`。

SQL 里没有"把 JSON 数组炸开成多行再分组"的简单写法（MySQL 8 要 `JSON_TABLE`，
MySQL 5.7 根本没有）。所以只能：

```java
List<String> tagsJsonList = ...selectObjs("tags");
Map<String, Long> counter = tagsJsonList.stream()
        .flatMap(json -> JSONUtil.toList(json, String.class).stream())   // 炸开
        .collect(Collectors.groupingBy(tag -> tag, Collectors.counting())); // 计数
```

**这就是这个设计的代价**：图片有多少张，就要把多少行 tags 读进内存。
10 万张图 = 10 万条 JSON 字符串 + 解析出来的所有标签对象。

如果数据量再大，正确做法是**反范式**：新建 `picture_tag(pictureId, tag)` 关联表，
或者把标签统计结果预计算到一张统计表里。这是典型的「用空间换查询效率」。

## 六、时间维度：把 createTime 折叠成一个值

按天/周/月分组，靠的是 MySQL 日期函数把同一区间的 `createTime` 映射成同一个值：

| 维度 | 表达式 | 返回类型 | 例 |
|---|---|---|---|
| 日 | `DATE_FORMAT(createTime, '%Y-%m-%d')` | String | `2026-09-10` |
| 周 | `YEARWEEK(createTime)` | Integer | `202636` |
| 月 | `DATE_FORMAT(createTime, '%Y-%m')` | String | `2026-09` |

然后 `GROUP BY period ORDER BY period ASC`，一个字段同时完成分组和排序。

**两个坑**：

1. `GROUP BY period` 用的是 **SELECT 别名**。这**不是 SQL 标准**，是 MySQL 的扩展。
   换到 Oracle / SQL Server 会报"无效标识符"。可移植的写法是把表达式再写一遍。
2. `YEARWEEK()` 返回的是 `202636` 这样的数字，前端直接展示会很难看；
   而且跨年周的归属依赖 `mode` 参数（默认 mode 0 = 周日为一周第一天），
   12 月 31 日可能被算进下一年的第 1 周。做报表时要显式确认口径。

## 七、大小分析：边界和复杂度

```java
if (size < 100 * KB)            counts[0]++;
else if (size < 500 * KB)       counts[1]++;
else if (size < 1024 * KB)      counts[2]++;
else                            counts[3]++;
```

两个细节：

1. **边界归属**：`<` 而不是 `<=`，所以 100KB 整落在第二段，1MB 整落在第四段。
   必须固定一套规则并写进测试，否则前后端对不上。
2. **一遍遍历**：笔记初版是 4 个 `stream().filter().count()`，遍历 4 遍列表。
   改成 `long[] counts` 一遍扫完，O(4n) → O(n)。

还有 `1024` vs `1000`：文件大小用 1024（KiB），但 UI 上常写 "KB"。
显示口径要统一，否则用户会质疑"为什么 1MB 的图算在 500KB-1MB 里"。

## 八、除零：笔记那版是直接 500（实测）

```java
double ratio = space.getTotalSize() * 100.0 / space.getMaxSize();
```

`maxSize = 0` 时：

```
500 * 100.0 / 0  = Infinity
NumberUtil.round(Infinity, 2)
  → java.lang.NumberFormatException: Unparseable number: "Infinity"

0 * 100.0 / 0    = NaN
NumberUtil.round(NaN, 2)
  → java.lang.IllegalArgumentException: Number is invalid!
```

也就是说**接口直接 500**，不是"返回一个奇怪的百分比"。

再往下一层：就算你不用 Hutool 取整，直接返回 `Double`，Jackson 默认会把它们写成**字符串**：

```
{"normal":50.0,"infinity":"Infinity","nan":"NaN"}
```

前端拿到的是 `"Infinity"` 这个字符串，`Number("Infinity")` 是 `Infinity`，
ECharts 仪表盘直接画崩，而且**不会报错**。

所以本章代码改成：

```java
private static Double percent(Long used, Long max) {
    if (used == null || max == null || max <= 0) return null;   // 明确告诉前端"没有比例"
    return NumberUtil.round(used * 100.0 / max, 2).doubleValue();
}
```

**规则：分母来自用户数据（配额、除数、平均值），就必须判零。**

## 九、`last()` 和 SQL 注入

```java
queryWrapper.last("LIMIT " + topN);
```

`last()` 是 MyBatis-Plus 里**唯一直接拼字符串进 SQL 尾部**的方法，不做参数绑定。

- 这里 `topN` 是 `Integer`，所以拼进去的一定是数字，安全。
- 如果哪天有人把 `topN` 改成 `String`（"前端传什么就传什么"），
  就是教科书级 SQL 注入：`LIMIT 10; DROP TABLE picture`。

真正的加固是**双重**的：类型是 `Integer` + 业务上把范围夹到 `[1, 100]`。
只靠类型不够，因为 `Integer.MAX_VALUE` 也能把数据库拖死。

对比：`#{topN}` 是预编译参数（安全），`${topN}` 和 `last()` 是字符串拼接（危险）。

## 十、分析类需求为什么都要缓存

分析 SQL 的特点是：**扫全表、算聚合、结果变化慢**。

- 用户点一次"分类分析"，可能扫 10 万行；
- 但 10 万行里可能 1 分钟才变一次。

所以标准做法是：

| 方案 | 适用 | 代价 |
|---|---|---|
| 不缓存 | 数据量小、实时性要求高 | 每次全表扫 |
| Redis / 本地缓存 + TTL | 大部分后台分析 | 结果有延迟，TTL 内是旧数据 |
| 定时任务预计算到统计表 | 日报、周报、排行榜 | 需要额外表和调度，实时性差 |

关键点是**缓存 key 必须包含查询范围**：`analyze:category:{queryAll}:{queryPublic}:{spaceId}`。
只按 `spaceId` 做 key，管理员查全空间的结果会污染普通用户的缓存——这是很常见的越权缓存 bug。

另外缓存要有**主动失效**：上传/删除图片后，这个空间的统计就该失效。
只靠 TTL，用户会出现"我刚传了图，分析里没有"。

## 十一、已知局限（这一版没做的）

1. **标签分析、大小分析全量读内存**——百万级图片会 OOM，需要反范式表或预计算。
2. **没有任何缓存**——每次请求都真查数据库。
3. **`/usage` 的全空间分支用 `selectObjs` 把每行 picSize 都读回 JVM 再 sum**，
   更大的数据量应该直接用 `SELECT COUNT(*), SUM(picSize)` 让数据库算完返回一行。
4. **`YEARWEEK` 的跨年口径**没处理。
5. 分析接口没有限流，被刷会打满数据库。

---

## 十二、三条工程习惯

1. **聚合结果的 Java 类型不要猜**，用 `Number` 接，或者先跑一条真 SQL 看列类型。
   （本章 `SUM → BigDecimal`、`YEARWEEK → Integer` 都是实测出来的，不是背的。）
2. **任何"分母"都要问一句"它能为 0 吗"**。除零在 Java 里不报错，
   拖到 Jackson 序列化或前端渲染时才炸，排查成本高得多。
3. **参数化查询是底线**：`#{}` 安全，`${}` / `last()` 是拼接。
   用拼接就必须自己保证「类型 + 范围」双重可控。

## 十三、验收复盘（8 题）

8 题一轮，结果 3 全对 / 3 半懂 / 1 错。三处认知偏差值得单独记下来，比记答案有用。

### 1. `SUM()` 的类型：不是 BIGINT，是 DECIMAL

真实探针输出（MySQL 8，本机 `a_picture` 库，10 行数据）：

```
columns: [1]category (VARCHAR)  [2]count (BIGINT)  [3]totalSize (DECIMAL)
row1:    category=null          count=10<Long>      totalSize=36970448<BigDecimal>
```

- `COUNT(*)` → BIGINT → `Long`
- `SUM(picSize)` → **DECIMAL → `BigDecimal`**。MySQL 把 `SUM` 提升到 `DECIMAL(65,0)`，
  因为求和可能溢出 BIGINT —— 65 位十进制，永远不会溢出。
- `(Long) row.get("totalSize")` → `ClassCastException: class java.math.BigDecimal cannot be cast to class java.lang.Long`

**怎么确认（从快到慢，三选一）**：

1. `System.out.println(row.get("totalSize").getClass())` —— 一行代码，最快
2. 数据库客户端跑同一句 SQL，看列头类型
3. `ResultSetMetaData.getColumnTypeName(i)`

**看 MyBatis 的 SQL 日志没用**：`StdOutImpl` 只打印 `Preparing / Parameters / Total`，
结果列的类型是 JDBC 驱动从 `ResultSetMetaData` 拿的，日志里根本没有。

> 这就是代码里统一用 `Number` 接聚合值的原因：**不需要提前知道它是谁，只需要知道它一定是 `Number`。**

### 2. 除零：浮点除法不抛异常

```java
int a = 5 / 0;         // ArithmeticException: / by zero   ← 只有整数除法
double b = 5.0 / 0;    // Infinity                         ← 静默
double c = 0.0 / 0;    // NaN                              ← 静默
```

`used * 100.0 / max` 里 `100.0` 是 double，整个表达式走浮点除法，
所以 **max=0 时不抛异常**，产生 `Infinity`，错误推迟到下一步。真实探针：

```
500 * 100.0 / 0 = Infinity
  → NumberUtil.round(Infinity, 2)
  → java.lang.NumberFormatException: Unparseable number: "Infinity"

0 * 100.0 / 0   = NaN
  → NumberUtil.round(NaN, 2)
  → java.lang.IllegalArgumentException: Number is invalid!
```

不用 Hutool 取整、直接把 `Double` 返回的话，Jackson 默认把非有限浮点数序列化成**字符串**：

```json
{"normal":50.0,"infinity":"Infinity","nan":"NaN"}
```

前端拿到 `"Infinity"`（字符串），ECharts 把仪表盘画崩，**控制台还不报错**。

> 「除零会报 500」只对了后半段。真实链条是：
> **除法不报错 → 取整报 500；跳过取整 → 前端静默崩溃。**
> 修复点只有一个：算之前判 `max == 0` 直接返回 null。

### 3. 缓存 key 少一个维度就是越权

`analyze:category:{spaceId}` 这种 key 是错的：`queryAll` / `queryPublic` 时 `spaceId` 都是 null，
两个完全不同的结果集撞进同一个 key。正确写法：

```
analyze:category:{queryAll}:{queryPublic}:{spaceId}
analyze:user:{queryAll}:{queryPublic}:{spaceId}:{userId}:{timeDimension}
analyze:rank:{topN}
```

判断标准：**key 里少一个参数，就会有一类请求读到别人的结果。**

失效同理 —— 一张图变化会同时改变三个范围（所在空间 / 公共图库 / 全空间），
删的是一组 key，不是一个。

### 4. 答题习惯：先复述题干的主语

这一轮 Q5 问「冗余字段会**算错**什么」，答成了「公共图库难查」；
第 9 章 Q7 问「并发保存会不会**互相覆盖**」，答成了「重复计费」。

两次都是**问题问 A 的代价，答成 B 的困难**。检查法：答题前把题干的主语 + 谓语抄一遍，
确认自己答的是同一件事。
