# 图片协同编辑 —— 知识点

> 这一章是项目的「亮点功能」：多人同时打开同一张图，一个人改，其他人实时看到。
> 技术上踩了三块地：**WebSocket 长连接**、**事件驱动的消息分发**、**把并发冲突用业务设计消掉**。

## 一、这段做了什么

### 新增文件

| 文件 | 作用 |
|---|---|
| `manager/websocket/model/PictureEditRequestMessage` | 前端 → 后端：`{type, editAction}` |
| `manager/websocket/model/PictureEditResponseMessage` | 后端 → 前端：`{type, message, editAction, user}` |
| `manager/websocket/model/enums/PictureEditMessageTypeEnum` | INFO / ERROR / ENTER_EDIT / EXIT_EDIT / EDIT_ACTION |
| `manager/websocket/model/enums/PictureEditActionEnum` | ZOOM_IN / ZOOM_OUT / ROTATE_LEFT / ROTATE_RIGHT |
| `manager/websocket/WsHandshakeInterceptor` | 握手前鉴权 + 把 user / pictureId 塞进会话属性 |
| `manager/websocket/PictureEditHandler` | 连接建立 / 收消息 / 连接关闭 三个时机 |
| `manager/websocket/WebSocketConfig` | 把 `/ws/picture/edit` 绑到 handler + interceptor |
| `common/SpaceUserPermissionConstant` | 权限串常量，避免枚举和注解各写一份 |

`pom.xml` 加了 `spring-boot-starter-websocket`。

### 一条连接的完整生命周期

```
前端 new WebSocket("/api/ws/picture/edit?pictureId=100")
        │
        ├─【握手】WsHandshakeInterceptor.beforeHandshake
        │    ① pictureId 有没有 / 是不是数字
        │    ② 登录了吗
        │    ③ 图片存在吗，属于团队空间吗
        │    ④ 这个成员有 picture:edit 吗
        │    → 全部通过：attributes.put("user"/"userId"/"pictureId")
        │    → 任一失败：return false，握手被拒（前端只看到连接失败）
        │
        ├─【连接成功】afterConnectionEstablished
        │    把 session 加进 pictureSessions[pictureId]，广播「XX加入编辑」
        │
        ├─【收消息】handleTextMessage
        │    ENTER_EDIT / EDIT_ACTION / EXIT_EDIT / 其他 → ERROR
        │
        └─【断开】afterConnectionClosed
             如果他正握着编辑锁 → 释放
             把 session 摘掉，最后一个人走了连 key 一起删
             广播「XX离开编辑」
```

## 二、为什么是 WebSocket

实时通讯的三条路：

| 方案 | 怎么工作 | 适不适合协同编辑 |
|---|---|---|
| 长轮询 | 前端发请求，服务端 hold 住不给响应，等有数据或超时再返回，前端立刻再发一个 | 每次事件都要一次 HTTP 往返，头部开销大，服务端要 hold 一堆线程 |
| SSE | 服务端单向推送，`text/event-stream` 长响应 | 只能服务端 → 客户端，而编辑动作必须客户端 → 服务端，还得另开一个 HTTP 接口 |
| **WebSocket** | 一次 HTTP Upgrade 握手（101 Switching Protocols），之后升级成 TCP 上的全双工帧 | ✅ 双向、低开销、延迟最低 |

**关键一点：WebSocket 是借 HTTP 建的，不是替代 HTTP。** 握手那一次仍然是标准 HTTP 请求（能带 Cookie、能过网关、能走 443），拿到 101 之后才切换协议。所以「WebSocket 走的不是 HTTP 端口」是错的。

### 为什么不用 STOMP / SockJS

| 实现方式 | 代价 |
|---|---|
| 原生 `WebSocketHandler` | 手动管会话与分发，但轻、可控 |
| STOMP + SockJS | 自带订阅/广播模型，配置重、要外部 broker 才香 |
| WebFlux Reactive | 高并发强，学习曲线陡，和现有 Servlet 栈混用成本高 |

本项目并发不高、消息模型只有「一张图一个房间」，用原生最划算。

## 三、协同冲突：这把锁是怎么想出来的

### 冲突长什么样

两个人同时快速点十次旋转，事件是并发的：

```
A: 右旋 → 右旋 → 右旋 ...
B: 左旋 → 左旋 → 左旋 ...
```

如果没有顺序保证，两人的操作以任意顺序交错落到画面上，**每个人看到的最终角度都不一样**。这就是协作冲突。

### 两条路的取舍

**路 A：OT / CRDT 算法。** 把每个操作建模成「对某个位置上的一次变换」，服务端做转化（Transformation），让不同顺序应用得到同一结果。语雀、Figma 这类产品走的就是这条路。
- 代价：算法复杂度和业务形态强耦合。文本是「一维位置」，图片旋转是「一个角度值」，两者模型完全不同；协作密度越高越难。

**路 B：同一时刻只允许一个人编辑。** 给「编辑这张图」加一把锁，其他人只能实时看，不能动。想编辑得等对方退出。
- 代价：牺牲了并行度。协作文档那种「两人同时打字」做不到。

**本项目选 B。** 理由不是 B 更高级，而是：**用业务设计把并发问题从源头消掉，比用算法在事后补救便宜得多。** 一句「同一时刻只能一个人编辑」，省掉了一整套 OT 引擎。

> 这也是一个通用思路：**面试/设计题里遇到「并发冲突怎么办」，先问「能不能不让它并发」，再考虑加锁，最后才是算法。**

## 四、编辑锁怎么写才不会漏

### 错误写法（笔记原版）

```java
if (!pictureEditingUsers.containsKey(pictureId)) {   // ① 检查
    pictureEditingUsers.put(pictureId, user.getId()); // ② 写入
}
```

这是典型的 **check-then-act（TOCTOU，Time-of-Check to Time-of-Use）**：

```
时刻  t1        t2              t3
线程 A   containsKey → false
线程 B                   containsKey → false
线程 A                           put(A)   ← 拿到了
线程 B                                   put(B)   ← 也拿到了，A 的锁被覆盖
```

`ConcurrentHashMap` 保证单次操作是原子的，**不保证「两次操作合起来」是原子的**。换成 `Hashtable` 也一样。

### 正确写法

```java
Long currentEditor = pictureEditingUsers.putIfAbsent(pictureId, user.getId());
if (currentEditor == null) {
    // 抢到了
} else if (currentEditor.equals(user.getId())) {
    // 自己重复进入，幂等放行
} else {
    // 别人正在编辑
}
```

`putIfAbsent` 是**一条**原子操作（CAS 实现），检查和写入在同一把锁的语义里完成。

> 通用规则：**凡是「先判断再修改」的共享状态，都要问自己能不能压成一个原子操作。**
> 常见替代：`putIfAbsent`、`computeIfAbsent`、`ConcurrentHashMap.merge`、数据库唯一索引 + `insert`。

### 锁的释放必须挂在三个地方

| 时机 | 谁触发 |
|---|---|
| 用户主动点「退出编辑」 | `EXIT_EDIT` 消息 |
| 用户直接关页面/断网 | `afterConnectionClosed` |
| 服务端重启 | 内存全清（见「已知局限」） |

**最容易漏的是第二个。** 如果只在 `EXIT_EDIT` 时释放，用户直接关掉浏览器，这张图就永远锁死，谁都进不来——而且是**不可自愈**的，只能重启服务。

## 五、两张表管两件事

```java
// 谁正在编辑这张图（锁）
Map<Long, Long> pictureEditingUsers;          // pictureId -> userId

// 谁连在这张图上（广播名单）
Map<Long, Set<WebSocketSession>> pictureSessions;  // pictureId -> sessions
```

- **按 pictureId 分区**：不同图片的协作互不影响，天然隔离。
- **必须用 `ConcurrentHashMap` + `ConcurrentHashMap.newKeySet()`**：`afterConnectionEstablished` 和 `handleTextMessage` 在不同的线程上跑，普通 `HashMap`/`HashSet` 会丢数据甚至在扩容时死循环。
- **最后一个人走了要 `remove` 整个 key**：不删的话 map 随着「打开过的图片数」单调增长，是缓慢的内存泄漏。

### 广播的三个细节

1. **`excludeSession`**：执行编辑操作的人不该收到自己的操作，否则前端本地做一次 + 收到消息再做一次 = **双倍旋转**。
2. **`isOpen()` 先判**：会话可能已经半死，往里写会抛 `IOException`。
3. **单个会话失败要 catch 掉**：一个坏会话不能中断整轮循环，否则排在它后面的所有人都收不到。

## 六、握手期鉴权：为什么身份必须在这里定下来

WebSocket 连上之后，**没有「请求」这个概念了**。`handleTextMessage` 里你手上只有一个 `WebSocketSession`，拿不到 `HttpServletRequest`，也就拿不到 Cookie / Session 里的登录用户。

所以身份必须在握手那一刻确定，然后塞进 `session.getAttributes()`：

```java
attributes.put("user", loginUser);
attributes.put("userId", loginUser.getId());
attributes.put("pictureId", pictureId);  // 注意转成 Long
```

### 四道关卡缺一不可

| 关卡 | 不做的后果 |
|---|---|
| pictureId 存在且合法 | 后面 `Long.parseLong` 抛异常，或者拿着 null 去查库 |
| 用户已登录 | 匿名连接进来能看别人团队空间的图 |
| 图片存在 + 属于**团队空间** | 私有空间、公共图库的图被拉进协同通道（需求上只对团队空间开放） |
| 成员有 `picture:edit` | 浏览者（只有 `picture:view`）也能进来改图，权限体系白做 |

第 4 关复用的是第 11 章做好的 `spaceUserService.getPermissionList(userId, spaceId)`——**鉴权逻辑不要在两处各写一份**，否则迟早不一致。

### `pictureId` 为什么要显式转 Long

`getParameter()` 返回的是 `String`。如果直接 `attributes.put("pictureId", pictureIdStr)`，后面 `(Long) attributes.get("pictureId")` 会抛 `ClassCastException`。这种错在运行时才炸，而且报的是「类型转换失败」，看不出是握手时埋的雷。

## 七、消息协议：五种类型与各自的广播范围

| 类型 | 谁发 | 广播给谁 | 说明 |
|---|---|---|---|
| `INFO` | 后端 | 全房间 | 加入 / 离开通知 |
| `ERROR` | 后端 | **只发给当事人** | 抢锁失败、消息类型错误、非法操作 |
| `ENTER_EDIT` | 后端（由 `ENTER_EDIT` 请求触发） | 全房间 | 其他人收到后锁定 UI |
| `EXIT_EDIT` | 后端（由 `EXIT_EDIT` 请求触发） | 全房间 | 其他人收到后解锁 UI |
| `EDIT_ACTION` | 后端（由 `EDIT_ACTION` 请求触发） | **除自己外**的全房间 | 其他人照着做旋转/缩放 |

**注意 `ERROR` 的广播范围是「只给当事人」。** 广播给所有人会让别人莫名其妙看到一条不是自己造成的错误提示。

### 消息类型为什么不用 `valueOf`

```java
PictureEditMessageTypeEnum typeEnum = PictureEditMessageTypeEnum.valueOf(type);  // ❌
```

前端传了一个不认识的值（版本不一致、抓包重放、手滑），`valueOf` 直接抛 `IllegalArgumentException`。这个异常从 `handleTextMessage` 冒出去，Spring 会**关掉这条连接**——用户只是发错了一条消息，却把整个协作会话搞断了。

改成 `getEnumByValue()` 返回 `null`，然后回一条 `ERROR` 就好：**脏数据应该被拒绝，但不该打断连接。**

## 八、WebSocket 的四个工程坑

### 坑 1：`sendMessage` 不是线程安全的

`WebSocketSession.sendMessage` 内部调 `getBasicRemote().sendText()`，同一个会话被两个线程同时写会抛：

```
java.lang.IllegalStateException: The remote endpoint was in state [TEXT_FULL_WRITING]
```

在我们的场景里，广播线程 + 处理线程完全可能同时给同一个会话发消息。

**Spring 自带的解法**是 `ConcurrentWebSocketSessionDecorator`（内部排队 + 超时丢弃）。本章用的是更朴素的 `synchronized (session)`：

```java
private void sendText(WebSocketSession session, String json) throws IOException {
    synchronized (session) {
        session.sendMessage(new TextMessage(json));
    }
}
```

够用，但**所有发送必须走这一个出口**，不然加锁等于没加。

### 坑 2：一个坏会话拖垮整轮广播

```java
for (WebSocketSession session : sessionSet) {
    session.sendMessage(textMessage);   // ❌ 谁抛异常，后面所有人都收不到
}
```

必须逐条 try-catch。**广播是「尽力而为」，不是「全有或全无」。**

### 坑 3：每条消息 new 一个 ObjectMapper

笔记原版在 `broadcastToPicture` 里 `new ObjectMapper()`。ObjectMapper 的构造和 `SimpleModule` 注册都有成本，而且它是**线程安全**的（读多写少场景下配置完成后可共享），没理由每条消息新建一个。

改成 `private static final ObjectMapper`，只在类加载时建一次。

### 坑 4：把 `Long` 直接序列化成数字

前端 JS 的 `Number` 是 IEEE 754 双精度，**只能精确表示 2^53 - 1 以内的整数**。雪花 id 是 19 位，直接传数字会丢精度：

```
后端 1800000000000000001  →  前端 1800000000000000000
```

于是「按 id 找会话」「按 id 回查图片」全部错位。解法是序列化时把 `Long` 转成字符串：

```java
SimpleModule module = new SimpleModule();
module.addSerializer(Long.class, ToStringSerializer.instance);
module.addSerializer(Long.TYPE, ToStringSerializer.instance);  // 基本类型 long 也要
```

> 这也是为什么很多大厂接口里 id 一律是 `"1234567890"` 这种字符串。**不是他们不爱用数字，是 JS 装不下。**

## 九、Disruptor 那一节在解决什么（本章未实现）

笔记的「扩展知识」引入了 Disruptor，先说清它要解决的真问题：

**Spring WebSocket 里，`handleTextMessage` 跑在该会话的 I/O 线程上，而且同一个连接的多条消息是串行处理的。** 如果处理逻辑里有耗时操作（查库、发远程调用），这条连接的后续消息全被堵住。

类比：Spring MVC 里一个接口耗时 3 秒，Tomcat 的工作线程就被占 3 秒；并发一高，线程池耗尽。

解法是「异步化 + 保序」：开一个线程池专门处理，消息先进队列，保证顺序消费。`ThreadPoolExecutor + BlockingQueue` 就能做。

Disruptor 是这条路上的**高性能版本**：

| 特性 | Disruptor | BlockingQueue |
|---|---|---|
| 并发控制 | 无锁（CAS + 内存屏障） | `ReentrantLock` |
| 内存 | 固定大小的环形数组，复用对象 | 动态数组/链表，频繁分配 |
| 延迟 | 纳秒级 | 毫秒级 |
| GC 压力 | 极低 | 较高 |

它还顺带解决了一件队列做不到的事：**优雅停机**。`@PreDestroy` 里 `disruptor.shutdown()` 会把队列里剩余任务跑完再退出，避免服务重启时丢消息。

> 本章没做这一步：当前处理逻辑只有内存操作（改 map + 发消息），没有阻塞点，加 Disruptor 是纯增加复杂度。等真接了「操作落库」「调 COS」再说。

## 十、已知局限

| # | 局限 | 后果 | 怎么补 |
|---|---|---|---|
| 1 | 状态全在单机内存 | 多实例部署时，两个用户连到不同机器互相收不到消息 | 粘性会话（同一图片固定路由到同一实例），或 Redis Pub/Sub 跨实例广播 |
| 2 | 新加入的人看不到「已经改到什么程度」 | 别人转了 90°，你进来看到的是原图 | 每次 `EDIT_ACTION` 记一条到 Redis，新人进来先回放 |
| 3 | 登录态失效后连接还活着 | 用户退出登录，WS 仍能继续发编辑消息 | 心跳时校验 Sa-Token 登录态，失效主动 `close()` |
| 4 | 没有心跳 | Nginx 默认 `proxy_read_timeout 60s`，闲置连接会被掐断 | 前端定时发 ping / 后端配 `ping` 消息 |
| 5 | 没有消息序号 | 极端情况下消息乱序到达，前端无法识别 | 每条消息带自增 seq，前端丢弃旧 seq |
| 6 | `setAllowedOrigins("*")` | 任意站点都能发起连接（配合 Cookie 有 CSRF 风险） | 生产改成域名白名单 |
| 7 | 断线不重连 | 网络抖一下就得手动刷新 | 前端指数退避重连 |

## 十二、三条工程习惯

1. **「先判断再修改」的共享状态，先问能不能压成一条原子操作。** `containsKey` + `put` 在并发下永远是错的，`putIfAbsent` 才是答案。
2. **锁必须挂在「所有可能的退出路径」上，尤其是异常和断线。** 只在正常路径释放的锁，迟早会锁死。
3. **跨语言传 `Long`，一律转字符串。** JS 的 `Number` 装不下 64 位整数，这不是「可能有」的风险，是「一定会」的精度丢失。
