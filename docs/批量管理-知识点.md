## 0. 这一章做了什么

用户勾选多张图片，一次性修改它们的 **分类 / 标签 / 名称**。

```java
// SpacePictureServiceImpl.editPictureByBatch  ——  四步
1. 参数校验           spaceId > 0、pictureIdList 非空
2. 空间权限校验       spacePermissionHelper.checkSpaceAccess(spaceId, loginUser)
3. 只查必要字段       select("id","spaceId").eq("spaceId", spaceId).in("id", pictureIdList)
4. 填充 + 一次批量写  fillPictureWithNameRule(...) → pictureMapper.updateById(pictureList)
```

四个优化考量点（笔记 1744-1751 行）：

| # | 考量 | 代码落点 |
|---|---|---|
| 1 | 数据校验 + 空间权限 | `ThrowUtils.throwIf` + `checkSpaceAccess` |
| 2 | 只 select 需要字段 | `.select("id","spaceId")` |
| 3 | 事务原子性 | `@Transactional(rollbackFor = Exception.class)` |
| 4 | 批量更新而非循环 | `updateById(Collection)` |

## 1. 批处理到底省了什么

**结论：省 RTT 和客户端映射，不省服务端执行。**

| 成本项 | 批处理 | 原因 |
|---|---|---|
| 网络往返（RTT） | ✅ 省 | 100 条 → 1 次 flush |
| 服务端 SQL 解析/执行 | ❌ 不省 | 还是 100 条 UPDATE，逐条执行 |
| 客户端 resultMap 映射 | ✅ 省 | 不需要为每条构造返回对象 |
| JDBC 往返开销 | ✅ 省 | 走 `BatchExecutor`，攒够了再 flush |

**关键差异**：INSERT 能被驱动合并成一条多值语句（`INSERT ... VALUES (...),(...)`），
UPDATE **不能**——标准 SQL 没有「一条语句按不同条件改不同值」的语法。
所以批量 UPDATE 的性能天花板明显低于批量 INSERT。

## 2. `NOT_NULL` 更新策略（默认）

```java
// mybatis-plus-core 3.5.16，GlobalConfig$DbConfig
private FieldStrategy updateStrategy = FieldStrategy.NOT_NULL;
```

**机制：字段为 `null` 时，该字段不出现在 `SET` 子句里。**

实测生成的 SQL（只传了 name）：

```sql
UPDATE picture SET name=? WHERE id=? AND isDelete=0
```

> 注意：不是「合并」，是「**根本没写进去**」。

### 安全性的隐式依赖

这个写法能安全，靠的是**两道锁，代码里一行都没写**：

1. `updateStrategy = NOT_NULL`（默认值，`application.yml` 未覆盖）
2. 数据库 `NOT NULL` 约束兜底

把策略改成 `always` 会怎样？实测：

```sql
UPDATE picture SET type=?, url=?, previewUrl=?, ..., updateTime=? WHERE id=? AND isDelete=0
→ SQLIntegrityConstraintViolationException: Column 'type' cannot be null
```

**结论**：`NOT NULL` 列会直接报错（数据保住了）；
真正危险的是 **nullable 列**（`previewUrl`、`introduction`、`category`、`tags`、`picSize`、
`picWidth`、`picHeight`、`picScale`、`picFormat`、`spaceId`）——它们会被**静默写成 null**。

### 冷知识

`isDelete` 即使策略是 `ALWAYS`，也**被排除在 `SET` 之外**，只出现在 `WHERE` 里。
`@TableLogic` 字段有独立保护，实体 update 改不动它——想复活必须用 `UpdateWrapper.set("isDelete", 0)`。

## 3. 事务登记（enlistment）

**问题：`pictureMapper.updateById(Collection)` 自己开 session 自己 commit，为什么还会跟着 Spring 事务回滚？**

五步链（javap 验证）：

```
1. MybatisBatch.execute()
     → SqlSessionFactory.openSession(ExecutorType, boolean)
     → SqlSession.flushStatements()
     → SqlSession.commit()

2. 但这个 SqlSessionFactory 是 Spring 造的，Environment 里装的是
     MybatisSqlSessionFactoryBean → new SpringManagedTransactionFactory()

3. 所以 openSession 出来的事务实现是 SpringManagedTransaction，
   取连接走 DataSourceUtils，并记录 isConnectionTransactional

4. SpringManagedTransaction.commit()：
     getfield isConnectionTransactional
     ifne 42          ← 为 true 直接跳过，不 commit

5. 「批量自己提交」被静默取消，提交权交回 Spring → 外层回滚，批量一起回滚
```

**准确说法**：不是「有 `@Transactional` 注解所以会回滚」，
是「**批量的 session 被 Spring 事务管理器接管了，它自己的 commit 变成空操作**」。

> 教训：这个结论我第一次搞错了——`javap` 搜了 `mybatis-plus-extension-3.5.9.jar`（jar 和包名都错），
> 搜不到就下了「不参与事务」的结论。**负面结论不能靠「我没找到证据」支撑。**

### 部分失败也会整批回滚

实测：3 条记录，第 3 条 `picFormat` 塞 5000 字符（列 `varchar(32)`）：

```
→ org.apache.ibatis.exceptions.PersistenceException
→ 三条全部保持原值，无部分残留
```

`PersistenceException` 是 `RuntimeException` 子类，**不写 `rollbackFor` 也会回滚**。

## 4. `rollbackFor`

Spring 默认规则（`DefaultTransactionAttribute.rollbackOn`）：

| 异常类型 | 不加 `rollbackFor` | 加 `rollbackFor = Exception.class` |
|---|---|---|
| `RuntimeException` 及子类 | 回滚 | 回滚 |
| `Error` 及子类 | 回滚 | 回滚 |
| **受检异常**（`Exception` 非 `RuntimeException`） | **不回滚，照常提交** | 回滚 |

**`rollbackFor = Exception.class` 的意义：把受检异常也纳入回滚范围。**

对本项目是**防御性**的（MyBatis 把 SQL 错误包成 `PersistenceException`，本来就回滚）。
真正救命的是哪天写了 `throws IOException` 的方法——不加就会留下半截写入。

## 5. 自调用失效

**`@Transactional` 靠 AOP 代理实现。`this.method()` 不走代理，注解形同注释。**

```
Controller ──→ [代理对象] ──→ TransactionInterceptor ──→ [真实对象].method()   ✅ 有事务
[真实对象].method() ──this──→ [真实对象].other()                             ❌ 无事务
```

**「传播性」是另一个概念**：`REQUIRED` / `REQUIRES_NEW` / `NESTED` 讲「已有事务时怎么办」，
不解决「这次调用能不能进事务」。

三个解法：
1. 拆到另一个 bean（推荐）
2. 注入自己（`@Lazy @Autowired private XxxServiceImpl self;`）
3. `TransactionTemplate` 编程式

**判断标准一句话：调用方是不是「另一个 bean」。**

本项目 `editPictureByBatch` 由 `SpacePictureController` 调用，跨 bean，走代理，事务正常。

## 6. 并发的三个坑

### 6.1 死锁（ABBA）

A 顺序 `[1,2]`，B 顺序 `[2,1]`：

| 时刻 | 事务 A | 事务 B |
|---|---|---|
| t1 | 锁住 id=1 | |
| t2 | | 锁住 id=2 |
| t3 | 等 id=2 ⏳ | |
| t4 | | 等 id=1 ⏳ |

InnoDB 死锁检测回滚代价小的一方：`Deadlock found when trying to get lock`。

**解法：更新前按 id 升序排序。**

```java
pictureList.sort(Comparator.comparing(Picture::getId));
pictureMapper.updateById(pictureList);
```

### 6.2 异步线程 + 事务

```java
CompletableFuture.runAsync(() -> pictureService.editPictureByBatch(request));
//                                  ↑ 注入的代理 → @Transactional 生效
```

**生效，但是「另一个事务」**——Spring 事务绑在 ThreadLocal 上，跨线程传不过去。

| 风险 | 说明 |
|---|---|
| 外层回滚救不了它 | 异步那边已提交，数据半新半旧 |
| 失败静默 | 异常包在 Future 里，不 `.join()` 就消失 |
| 上下文丢失 | `RequestContextHolder`、登录用户、TraceId 全是 null |
| 打满公共池 | 默认 `ForkJoinPool.commonPool()`，影响整个 JVM |

**若写成 `this.editPictureByBatch(...)` 则是自调用，真的不生效——两个坑叠加。**

### 6.3 并发改名

`count` 是 `fillPictureWithNameRule` 内的**局部变量**，每个请求各有一份：

```java
long count = 1;
for (Picture picture : pictureList) {
    picture.setName(nameRule.replaceAll("\\{序号}", String.valueOf(count++)));
}
```

两个请求同时跑 → 各自从 1 数到 100 → 都生成「图片1…图片100」。
`picture.name` **没有唯一约束**（只是 `varchar(128) NOT NULL`）。

**本质**：`count` 是「请求内序号」，语义上就没有并发保证。三个方向：
1. 接受它（名字只给人看，唯一性靠 id）—— 绝大多数图库这么做
2. 唯一索引 + 冲突重试
3. 全局序列（`FOR UPDATE` / Redis 自增）—— 必然引入锁竞争，与批量更新初衷相悖

## 7. 字符串替换：`replaceAll` vs `replace`

| 写法 | 结果 |
|---|---|
| `nameRule.replaceAll("{序号}", ...)` | ❌ `PatternSyntaxException: Illegal repetition`（`{}` 是正则量词） |
| `nameRule.replaceAll("\\{序号}", ...)` | ✅ 可用（但仍是正则） |
| `nameRule.replace("{序号}", ...)` | ✅ 推荐（纯字面量，无正则开销） |

**替换串的坑**：`replaceAll` 的第二个参数会解析 `$1`、`\` 等转义：

```java
"a".replaceAll("a", "$1")   → IndexOutOfBoundsException（当成组引用）
"a".replace("a", "$1")      → "$1"（原样输出）
```

**规则：替换的是用户输入 → 一律用 `replace`。** 只有真需要正则匹配时才用 `replaceAll`。

## 8. `updateById(Collection)` 的返回值

**签名不是 `int`**：

```java
List<org.apache.ibatis.executor.BatchResult> updateById(Collection<T> entityList);
```

`BatchResult` API：`getMappedStatement` / `getSql` / `getParameterObject` / `getParameterObjects` /
`getUpdateCounts` / `setUpdateCounts` / `addParameterObject`（**没有 `getStatement()`**）。

`getUpdateCounts()` 是 JDBC 批量语义：

| 值 | 含义 |
|---|---|
| `>= 0` | 实际影响行数（**0 也是合法值**） |
| `-2` | `SUCCESS_NO_INFO`：执行了但驱动报不出准确行数 |
| `-3` | `EXECUTE_FAILED`：该条失败 |

### 丢弃它的风险

**`UPDATE ... WHERE id=? AND isDelete=0` 影响 0 行时不报错**。什么时候是 0 行？
id 不存在、图已被逻辑删除、图不属于该空间（被 `.eq("spaceId")` 过滤）。

这些**全被静默吞掉**，而方法最后无条件 `return true`。
前端收到 `true`，以为 5 张全改了，实际可能只改了 3 张。

**注意区分「会错」和「看不见」**：失败会抛 `PersistenceException`（实测），
所以数据不会错，错的是**可观测性**。

## 9. 大 IN 列表

5 万个 id 一次 `.in("id", list)` 的后果：

| # | 后果 | 说明 |
|---|---|---|
| 1 | SQL 文本过大 | `max_allowed_packet`（5.7 默认 4MB / 8.0 默认 64MB）→ `PacketTooBigException` |
| 2 | 优化器成本暴涨 | 5 万个常量做 range 分析；列表过大时**可能放弃索引走全表扫描** |
| 3 | **锁范围 → 长事务** | 一条 UPDATE 改 5 万行，行锁持有到提交；undo 膨胀、主从延迟全来 |
| 4 | 应用层内存 | JSON 反序列化 + MyBatis 拼 SQL + 驱动参数数组，三份并存 |

> 因果链是：**id 多 → 改的行多 → 事务长 → undo 膨胀**。
> 不是「IN 列表长」直接导致 undo 膨胀。

**正确做法：分批（每批 500~1000），每批一个独立短事务。**

注意「批处理」和「分批」是两件事：
- `ExecutorType.BATCH` 省的是 **RTT**
- 分批省的是 **锁和内存**

## 10. `rewriteBatchedStatements`

连接串加 `rewriteBatchedStatements=true` 后：

| 语句类型 | 效果 |
|---|---|
| **INSERT** | ✅ 合并成一条多值语句，**真正的加速**（服务端只解析一次） |
| **UPDATE / DELETE** | ⚠️ 收益很小——SQL 没有多行 UPDATE 语法，驱动无法合并，最多拼包减少网络往返 |

**与 `-2` 的关系**：合并后驱动无法逐条报告影响行数，
`getUpdateCounts()` 返回 `SUCCESS_NO_INFO (-2)`。
**开了这个参数，「用返回值统计成功条数」就废了。**

## 11. 两条工程习惯（比上面任何一条都值钱）

### 11.1 负面结论只能靠「能真正失败的实验」

「它不会 X」这种结论，**不能**靠「我搜了没找到」来支撑。
本章的 enlistment 结论就是活教训：搜错 jar 就下了反面结论，被实验推翻。

### 11.2 `UPDATE` 影响 0 行不报错

逻辑删除、权限过滤、id 不存在——全是**静默**的。
凡是「改了多少行」有业务含义的地方，都要看返回值。
