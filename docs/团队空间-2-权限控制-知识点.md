## 二、为什么要有两套账号体系

项目里本来就有登录态：`HttpSession` 里存了一个 `User` 对象（第 3 章做的）。那为什么不直接复用它？

**因为两者要回答的问题不一样。**

- 原来的登录态回答的是：「**你是谁**」。它只有一个维度——一个浏览器一个用户。
- 团队空间要回答的是：「**你在这个空间里能干什么**」。它的维度是「用户 × 空间」——同一个人在不同空间角色不同。

而且 `space_user` 表天然是「用户 × 空间」的二维结构，它的登录态如果硬塞进原来的 Session，会变成：

```java
session.setAttribute("spaceRoles", Map<Long, String>); // spaceId -> role
```

这样能跑，但每加一个空间就要往 session 里塞一条，session 会无限膨胀，而且 Sa-Token 提供的注解、通配符、踢人下线这些能力一个都用不上。

### Sa-Token 的多账号体系是怎么做的

Sa-Token 的核心对象是 `StpLogic`，它内部维护一个 `loginType` 字符串。所有 API 都是「**这个 StpLogic 的**登录态」：

```java
StpUtil.login(10001);                 // 默认账号，loginType = "login"
StpKit.SPACE.login(10001);            // 空间账号，loginType = "space"
```

两者的 token 存在不同的 key 里（`satoken:login:token:xxx` vs `satoken:space:token:xxx`），**互不干扰**：默认账号登录着不代表空间账号登录着，反之亦然。

```java
public class StpKit {
    public static final String SPACE_TYPE = "space";
    /** 默认账号，和 StpUtil 是同一个对象 */
    public static final StpLogic DEFAULT = StpUtil.stpLogic;
    /** 空间账号，独立的一套 */
    public static final StpLogic SPACE = new StpLogic(SPACE_TYPE);
}
```

**为什么空间账号不用 `StpUtil`？** 因为 `StpUtil` 的 `loginType` 是 `"login"`，全项目共用。如果空间登录也用它，用户登录一次就等于同时登录了空间账号，那「两套账号」的设计就失去意义了。分开之后，将来做「QQ 登录 / 微信登录 / 手机号登录」也是同一个套路：每套账号一个 `StpLogic`。

> 注意：`DEFAULT` 这个字段在本项目里其实**没被用到**（用户的角色校验还是老办法 `@AuthCheck` + AOP）。留着它只是为了说明「多账号」这件事，以及以后迁移方便。

## 三、本段最难的问题：权限校验拿不到 spaceId

Sa-Token 判权的调用链是这样的：

```
StpKit.SPACE.checkPermission("picture:edit")
    └── 问 StpInterface.getPermissionList(loginId, loginType)
            └── 「这个用户在这个 loginType 下有哪些权限？」
```

问题来了：`getPermissionList` 只给你**用户 id** 和**账号类型**，**拿不到请求参数**。

可是「他有没有 `picture:edit`」这件事，答案完全取决于**是哪个空间**——他在 A 空间是 editor，在 B 空间是 viewer。没有 spaceId，这道题根本没法答。

### 三种解法

| 方案 | 做法 | 问题 |
|---|---|---|
| ① 在 `getPermissionList` 里重新读一遍请求体 | 从 `RequestContextHolder` 拿 request，再 `getInputStream()` 读 body | **流只能读一次**，读完了 Controller 就拿不到参数了 |
| ② 登录时把「所有空间的角色」塞进 token | `login(id, SaLoginModel.setExtra("spaces", map))` | 角色一改 token 就过期了；空间多了 token 巨大；管理员新建空间后要重新登录 |
| ③ **ThreadLocal 传上下文**（本项目采用） | 切面先解析请求 → 算出 spaceId → 放进 ThreadLocal → `getPermissionList` 从里面取 | 多线程/异步会丢（本项目都是同步请求，可接受） |

方案 ③ 就是 `SpaceUserAuthContextHolder` 存在的全部理由：

```java
public class SpaceUserAuthContextHolder {
    private static final ThreadLocal<SpaceUserAuthContext> CONTEXT = new ThreadLocal<>();
    public static void set(SpaceUserAuthContext c) { CONTEXT.set(c); }
    public static SpaceUserAuthContext get() { return CONTEXT.get(); }
    public static void clear() { CONTEXT.remove(); }
}
```

切面负责 `set`，`getPermissionList` 负责 `get`，`finally` 里 `clear`。**`clear` 不能省**——Tomcat 的线程是复用的，不清理就会把上一个请求的上下文带给下一个请求（也就是「串号」）。

## 四、请求体只能读一次：RequestWrapper 的来龙去脉

### 现象

`HttpServletRequest` 的 `getInputStream()` 背后是 socket 的字节流。**读一次就到头了**，第二次读返回空。所以：

```java
// 切面里
String body = ServletUtil.getBody(request);   // 读走了
// 到 Controller
public void edit(@RequestBody XxxRequest req) { ... }  // req 是 null 或报 400
```

这不是 Spring 的 bug，是 Servlet 规范：**请求体是一次性的**。

### 解法：包一层，把 body 缓存成字符串

```java
public class RequestWrapper extends HttpServletRequestWrapper {
    private final byte[] body;

    public RequestWrapper(HttpServletRequest request) throws IOException {
        super(request);
        this.body = IoUtil.readBytes(request.getInputStream());   // 只读这一次
    }

    @Override
    public ServletInputStream getInputStream() {
        ByteArrayInputStream in = new ByteArrayInputStream(body);
        return new ServletInputStream() { /* 把 ByteArrayInputStream 适配成 ServletInputStream */ };
    }

    @Override
    public BufferedReader getReader() {
        return new BufferedReader(new InputStreamReader(getInputStream(), StandardCharsets.UTF_8));
    }

    public String getBody() { return StrUtil.utf8Str(body); }
}
```

关键点：**每次 `getInputStream()` 都新建一个 `ByteArrayInputStream`**，所以下游想读几次都行。

### 为什么必须放在 Filter 里

因为包装要发生在**所有下游之前**——切面、`@RequestBody` 参数解析、拦截器，任何一个都不能先读到原始流。所以只能是最外层的 Filter：

```java
@Override
public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) {
    String contentType = request.getContentType();
    // 只包 JSON；multipart 不包，否则整个文件读进内存
    if (contentType != null && contentType.contains("application/json")) {
        chain.doFilter(new RequestWrapper((HttpServletRequest) request), response);
    } else {
        chain.doFilter(request, response);
    }
}
```

**两条硬规则：**

1. **multipart 绝对不能包。** 上传图片的请求体可能是几十 MB，缓存成 `byte[]` 直接把堆撑爆。这也是为什么 `@RequestPart` 的接口没事——它们不是 JSON，走的是 `ServletUtil.getParamMap` 那条路。
2. **Filter 类不要加 `@Component`。** Spring Boot 会把容器里所有 `Filter` 类型的 bean 自动注册一遍；如果同时又用 `FilterRegistrationBean` 手动注册，就会**注册两次**，请求被包两层（body 被复制两份，还多一次内存拷贝）。所以这个类故意是「普通类」，只通过 `FilterConfig` 里的 `FilterRegistrationBean` 注册。

```java
@Bean
public FilterRegistrationBean<HttpRequestWrapperFilter> httpRequestWrapperFilter() {
    FilterRegistrationBean<HttpRequestWrapperFilter> bean = new FilterRegistrationBean<>();
    bean.setFilter(new HttpRequestWrapperFilter());   // new 一个，不是注入
    bean.addUrlPatterns("/*");
    bean.setOrder(Integer.MIN_VALUE + 10);            // 排在最前面
    bean.setName("httpRequestWrapperFilter");
    return bean;
}
```

**为什么要 `setOrder(Integer.MIN_VALUE + 10)`？** 因为 Spring Session 的过滤器 Order 是 `-2147483598`。如果我们的包装器排在它后面，Session 过滤器先读了 body，我们的包装就没意义了。`Integer.MIN_VALUE + 10` 比它还小，保证第一个执行。

## 五、一次鉴权的完整链路

以 `POST /space/picture/edit` 为例：

```
① 用户请求带上 satoken: xxx
        ↓
② 请求进入 HttpRequestWrapperFilter → body 被缓存成 String
        ↓
③ 进入 SaSpaceCheckPermissionAspect.around()
        ↓
④ StpKit.SPACE.checkLogin()
   ├── 没带 token / token 过期  → 抛 NotLoginException  → 全局异常 → 40100
   └── 通过
        ↓
⑤ spaceUserService.getAuthContextByRequest()
   ├── 读 body（已经是缓存的了，随便读）
   ├── 反序列化成 SpaceUserAuthContext：spaceId / pictureId / spaceUserId / id
   └── 有 id 但没 spaceId 时，按路径前缀判断它是哪一类 id
        ↓
⑥ SpaceUserAuthContextHolder.set(ctx)
        ↓
⑦ StpKit.SPACE.checkPermission("picture:edit")
   ├── 调 StpInterfaceImpl.getPermissionList(userId, "space")
   │   ├── 从 Holder 拿 ctx
   │   ├── getSpaceIdFromContext(ctx) → spaceId
   │   └── spaceUserService.getPermissionList(userId, spaceId)
   │       ├── space 不存在 / user 不存在 → 空集合
   │       ├── 空间所有者 或 系统管理员 → admin 全部权限
   │       ├── 在 space_user 里 → 按角色取权限
   │       └── 不在 → 空集合
   ├── 权限集合不含 picture:edit → 抛 NotPermissionException → 全局异常 → 40101
   └── 通过
        ↓
⑧ finally { SpaceUserAuthContextHolder.clear(); }
        ↓
⑨ 进入 Controller，再进 Service（Service 里原有的 checkSpaceAccess 照常执行，是第二道防线）
```

### 第 ⑤ 步的细节：路径 → id 类型

很多接口只传一个 `id`，不传 `spaceId`。这个 id 到底是空间 id、成员记录 id，还是图片 id？只能看路径：

| 路径前缀 | id 的含义 | 怎么拿到 spaceId |
|---|---|---|
| `/picture/**` | 图片 id | 查 `picture.spaceId` |
| `/space/picture/**` | 图片 id | 查 `picture.spaceId` |
| `/spaceUser/**` | 成员记录 id | 查 `space_user.spaceId` |
| `/space/**` | 空间 id | 直接用 |

```java
String partUri = StrUtil.removePrefix(requestUri, contextPath + "/");
String moduleName = partUri.startsWith("space/picture")
        ? "spacePicture"
        : StrUtil.subBefore(partUri, "/", false);
```

**这里踩过一个坑**：如果只取第一段，`/space/picture` 会被判成 `space`，于是把**图片 id 当成空间 id** 去查权限——99% 的情况会算出「不是成员，没权限」（因为图片 id 和空间 id 大概率不相等），表现为「明明能看却 40101」，极难排查。

> 这也说明一个设计判断：**权限上下文依赖 URL 结构，是脆的**。更稳的做法是每个接口显式传 `spaceId`，或者把 spaceId 放进 URL（`/space/{spaceId}/picture/edit`）。本项目为了少改接口，选择了「猜路径 + 查库反查」。

## 六、权限矩阵

| 操作 | 公共图库（spaceId 为空） | 私有空间 | 团队空间 viewer | 团队空间 editor | 团队空间 admin | 空间所有者 / 系统管理员 |
|---|---|---|---|---|---|---|
| 看图 | ✅ | ✅（本人） | ✅ | ✅ | ✅ | ✅ |
| 传图 | ✅ | ✅（本人） | ❌ | ✅ | ✅ | ✅ |
| 改图 | ❌ | ✅（本人） | ❌ | ✅ | ✅ | ✅ |
| 删图 | ❌ | ✅（本人） | ❌ | ✅ | ✅ | ✅ |
| 管成员 | — | — | ❌ | ❌ | ✅ | ✅ |

几个刻意的选择：

1. **公共图库给 `picture:upload` 但不给 `edit` / `delete`。** 因为公共图库的「改删」依据是**所有权**（是不是我传的），不是空间角色——这条规则留在原来的 `checkPictureAuth` 里，Sa-Token 不管。如果这里也放开，就等于「任何登录用户能改任何人的公共图」。
2. **空间所有者不需要在 `space_user` 里有一条记录。** 11-A 创建团队空间时虽然会自动写一条 admin，但老数据、手工数据可能没有；用 `space.getUserId() == loginUser.getId()` 兜底，保证「自己的空间永远进得去」。
3. **系统管理员看所有空间。** 运营/客服需要排障能力。

## 七、为什么 `getRoleList` 返回空

Sa-Token 支持两种校验粒度：

```java
@SaCheckRole("admin")            // 按角色
@SaCheckPermission("picture:edit")  // 按权限
```

本项目只用后者，所以 `getRoleList` 一律返回空列表。

**为什么？** 因为角色是「权限的集合」，直接判角色意味着**权限规则散落在两个地方**：注解里写 `@SaCheckRole("admin")`，而「admin 有哪些权限」写在枚举里。将来加一个「运营」角色（能看不能改），你就得把注解从 `admin` 改成 `admin OR 运营`，改的是一个 Java 字符串——编译期发现不了拼错。

判权限则只依赖枚举里那张表：加角色只改枚举，接口注解不动。

```java
// 好：接口只关心「要什么能力」
@SaSpaceCheckPermission("picture:edit")

// 差：接口关心「谁有这能力」，角色一变就要改接口
@SaCheckRole("admin")
```

## 八、全局异常：为什么必须加这两个 handler

Sa-Token 抛的是 `NotLoginException` / `NotPermissionException`，它们**不是** `BusinessException`。如果不处理：

- 未登录访问 → 500「系统错误」
- 权限不足 → 500「系统错误」

前端拿到 500 会以为是服务挂了，不会去引导用户登录。所以：

```java
@ExceptionHandler(NotLoginException.class)
public BaseResponse<?> notLogin(NotLoginException e) {
    return Result.error(ErrorCode.NOT_LOGIN_ERROR);   // 40100
}

@ExceptionHandler(NotPermissionException.class)
public BaseResponse<?> noPermission(NotPermissionException e) {
    return Result.error(ErrorCode.NO_AUTH_ERROR);     // 40101
}
```

**40100 和 40101 必须分开**：

- 40100 = 你还没登录 → 前端跳登录页
- 40101 = 你登录了但没这个权限 → 前端提示「无权限」，**不要**跳登录页

混成一个，用户会陷入「明明登录了却一直让我登录」的死循环。

## 九、登录态同步：两套 Session 要一起维护

```java
// userLogin 里
request.getSession().setAttribute(UserConstant.USER_LOGIN_STATE, user);
StpKit.SPACE.login(user.getId());                                  // ① 发 token
StpKit.SPACE.getSession().set(UserConstant.USER_LOGIN_STATE, user); // ② 存用户信息

// userLogout 里
request.getSession().removeAttribute(UserConstant.USER_LOGIN_STATE);
StpKit.SPACE.logout();                                              // ③ 注销 token
```

**为什么第 ② 步要再存一份 user？** 因为 Sa-Token 的 session 里只认 `loginId`。如果别处想从 Sa-Token 这边拿到完整用户对象（比如以后的拦截器、日志），没有这一步就得再查一次库。

**为什么 ③ 不能省？** 只清 HttpSession 不清 Sa-Token，用户「退出登录」之后空间接口还能凭旧 token 调——退出等于没退。

**超时必须对齐：**

```yaml
spring:
  session:
    timeout: 300000s
sa-token:
  timeout: 300000    # 单位是秒
```

两个数不一样会出怪事：Sa-Token 先过期 → 用户在页面上还是登录状态，但一点空间功能就 40100。反过来 HttpSession 先过期 → 普通接口掉登录，空间接口还活着。

## 十、已知局限（都是 knowingly 留的）

1. **老用户要重新登录一次。** 本次改造前登录的用户，HttpSession 里有 `User`，但 Sa-Token 里没有 token，访问空间接口会 40100。
2. **强依赖 Redis。** `sa-token-redis-jackson` 把 token 存 Redis，Redis 挂了所有空间接口都挂。好处是多实例部署时 token 共享、重启不丢。
3. **权限只到「空间」粒度，没有分类级数据权限。** 「只看风景分类」这种需求，注解层面表达不了，得在查询条件里加 `AND category IN (...)`（见 11-A 的验收复盘第四节）。
4. **权限上下文靠 URL 前缀推断。** 新增接口如果路径不规范（比如 `/picture/space/xxx`），id 会被误判。
5. **`getPermissionList` 不检查空间是否被禁用。** 被禁用空间的成员仍然能通过 Sa-Token 这一层，真正拦住他们的是 Service 里的 `checkSpaceAccess`。如果将来有新接口只依赖注解、不走 helper，就会漏。
6. **每次请求固定 3 次查询**（space、user、space_user），没有缓存。可以加 Redis 缓存 + 角色变更时失效，但会引入「改了角色要等缓存过期」的一致性问题。
7. **没有做「角色变更后强制下线」。** 不过因为权限是每次现算的，改角色立即生效，所以影响不大。
8. **JSON body 全量缓存进内存。** 超大的 JSON 请求（比如一次传十万个 id 的批量操作）会占内存；multipart 已排除。

## 十一、三条工程习惯

1. **框架给的钩子拿不到数据时，先想「谁能在更早的位置把它算出来」。** `getPermissionList` 只给 userId，硬要在里面读 body 就是死路；往前挪一步到切面，问题就变成「怎么跨层传参」，那是 ThreadLocal 的标准场景。
2. **同一个类被框架自动注册过一次，就别再手动注册第二次。** `Filter`、`Servlet`、`Listener` 都有这个陷阱；判断方法很简单——「我这个类上有没有 `@Component` 家族注解」。
3. **异常翻译要保语义。** 框架抛的「未登录」和「无权限」是两个不同的用户动作，翻译成同一个错误码，前端就没法做正确的引导。

## 十三、验收复盘（7 题）

结果：**5 对 / 1 半懂 / 1 不会**（Q1✅ Q2❌ Q3⚠️ Q4✅ Q5✅ Q6✅ Q7✅）。

### 13.1 「缓存了字节」不等于「能再读一遍」（Q2）

实测（`ByteArrayInputStream`，JDK 11）：

```
A-1 read = [hello]      ← 复用同一个实例
A-2 read = []           ← 第二次读，空了
A-3 available = 0

B-1 read = [hello]      ← 每次 new 一个
B-2 read = [hello]      ← 第二次照样读得到

C   after reset = [hello]   ← 复用 + reset() 也能救回来
```

`ByteArrayInputStream` 内部有一个游标 `pos`，每 `read()` 一次往后推一格，推到头（`pos == count`）就永远返回 `-1`。

所以 `RequestWrapper` 里有两件不同的事：

| 做的事 | 解决什么 |
|---|---|
| `this.body = IoUtil.readBytes(request.getInputStream())` | **字节还在不在内存里** |
| `getInputStream()` 里每次 `new ByteArrayInputStream(body)` | **游标归不归位** |

只做第一件不做第二件，就会得到上面 A-2 的结果：**字节没丢，是读完了**。

如果改成返回同一个实例，后果依次是：切面读完 → 游标到末尾 → Controller 的 `@RequestBody` 读到空串 → 参数全 null 或反序列化报错；并发场景下两个线程抢同一个游标，还可能读到半截数据。

> 一句话：**可重复读 = 每次给读者一个新的游标，不是把字节存下来就完事。**

### 13.2 `@Component` + `FilterRegistrationBean` = 注册两遍（Q3）

Spring Boot 启动时 `ServletContextInitializerBeans` 会扫描容器里**所有 `Filter` 类型的 bean**，自动包装成 `FilterRegistrationBean` 注册进 Servlet 容器。所以：

```java
@Component   // ← 框架自动注册一次
public class HttpRequestWrapperFilter implements Filter { ... }

@Bean        // ← 又手动注册一次
public FilterRegistrationBean<HttpRequestWrapperFilter> ... { ... }
```

结果同一个过滤器注册两遍，请求依次穿过两层 `RequestWrapper`：第一层把 body 读进 `byte[]`，第二层再读一遍再拷一份。后果是全量内存翻倍，以及「某层读的是参数而不是流」时出现的诡异 null。

**判断规则**：类上有 `@Component` 家族注解，就别再写 `FilterRegistrationBean`；写了 `FilterRegistrationBean`，就让它当普通类。

**怎么发现注册了两遍**：启动日志搜 `Mapping filters:`（同一个类出现两次），或断点看 `FilterChain` 长度。

注意：`FilterRegistrationBean` 注册出来的同样是 Servlet 层过滤器，「加 `@Component` 就变成 Spring 的、不加就在 Servlet 层」这个理解是错的。

### 13.3 ThreadLocal 不 `remove()` 的双重代价（Q5）

**代价一：串号。** Tomcat 的线程是复用的，不 `clear()` 的话，下一个请求会拿到上一个请求的 `SpaceUserAuthContext`——用 A 的权限去判 B 的请求。这是功能 bug，而且是**偶发**的（只有拿到同一个线程才复现）。

**代价二：内存泄漏。** `ThreadLocalMap` 的 key 是 `ThreadLocal` 对象的**弱引用**，value 是**强引用**。线程常驻（Tomcat 工作线程活到进程结束），key 被 GC 后 value 仍挂在 map 里，永远不释放。这里 value 是带着三个实体对象的 `SpaceUserAuthContext`，泄漏起来很可观。

规范：**`ThreadLocal` 必须 `set` / `remove` 成对，`remove` 放 `finally`。**

### 13.4 其余四题

- **Q1**：`getInputStream()` 是一次性流（Servlet 规范），读一次就到头，第二次返回空。这正是要在 Filter 里包 `RequestWrapper` 的原因。
- **Q4**：multipart 不包，两层原因——① 内存：几十 MB 的 body 缓存成 `byte[]` 就是整个文件进堆，并发上传直接 OOM；② 没意义：Servlet 3.0+ 的 `getParameter()` 对 multipart 由容器自己解析，不需要读 body 流。同理 `x-www-form-urlencoded` 也不该包。
- **Q6**：40100（没登录）和 40101（登录了但没权限）对应两个不同的用户动作——前者跳登录页，后者只提示无权限。混成一个，用户会陷入「明明登录了却一直让我登录」的死循环。
- **Q7**：角色是权限的集合，判角色等于把权限规则拆到两个地方（注解里写角色名、枚举里写权限表）。判权限只需改枚举一处。另外 Sa-Token 的权限串支持通配符（`picture:*`、`picture:view:*`），比角色名表达力强得多。

### 13.5 这轮的三句话

1. **「缓存了数据」和「能再读一遍」是两件事。** 数据在、游标不在，照样读空。
2. **框架的自动注册 + 你的手动注册 = 两次。** 加 `@Component` 之前先问「这个类型框架会不会替我注册」。
3. **ThreadLocal 不 `remove` 的代价是双份的**：串号（功能 bug）+ 泄漏（内存 bug），两个都很难复现。
