## 1. 这一章做了什么

两个接口，一个异步流程：

| 接口 | 方法 | 作用 |
|---|---|---|
| `/picture/out_painting/create_task` | POST | 校验权限 → 调阿里云创建任务 → 返回 `taskId` |
| `/picture/out_painting/get_task` | GET | 按 `taskId` 查状态 → 成功后返回 `outputImageUrl` |

新增文件：

- `api/aliyunai/AliYunAiApi.java` —— 第三方调用收口
- `api/aliyunai/model/CreateOutPaintingTaskRequest.java` —— 发出去的请求体
- `api/aliyunai/model/CreateOutPaintingTaskResponse.java` —— 创建任务的返回
- `api/aliyunai/model/GetOutPaintingTaskResponse.java` —— 查询任务的返回
- `model/dto/picture/CreatePictureOutPaintingTaskRequest.java` —— 前端入参（`pictureId` + `parameters`）

改动：`PictureController`（两个端点）、`PictureService` / `PictureServiceImpl`（接口 + 实现 + `checkPictureAuth`）、`application.yml`（`aliYunAi.apiKey`）。

## 2. 核心：为什么必须是异步

扩图一次几十秒。如果做成同步接口：

1. **占住 Tomcat 线程几十秒**。默认 200 个工作线程，200 个并发扩图就把整个应用打满，连首页都打不开。
2. **网关/浏览器先超时**。Nginx `proxy_read_timeout` 默认 60s，浏览器也会先断。
3. **失败了重试代价高**。超时断开后服务端其实还在跑，用户再点一次就是重复计费。

所以阿里云这个接口**只支持异步**：`X-DashScope-Async: enable` 是必须的，不带你拿不到 `taskId`。

### 前端轮询 vs 后端轮询

笔记选**前端轮询**。后端轮询会退化成：

```java
while (true) {
    Thread.sleep(2000);      // 线程在这里干等
    if (done) break;
}
```

线程没释放，只是把「等」从 HTTP 连接搬到了应用线程里，问题没解决。而且 Tomcat 线程池是共享资源，一个用户的轮询会拖累所有人的请求。

**通用规律**：只要等的是外部耗时操作，就不要让线程停在那里等。

## 3. 两个接口的调用契约

### 创建任务

```
POST https://dashscope.aliyuncs.com/api/v1/services/aigc/image2image/out-painting
Authorization: Bearer <apiKey>
X-DashScope-Async: enable
Content-Type: application/json
```

```json
{
  "model": "image-out-painting",
  "input": { "image_url": "https://..." },
  "parameters": { "x_scale": 1.5, "y_scale": 1.5, "output_ratio": "16:9" }
}
```

返回：

```json
{ "request_id": "...", "output": { "task_id": "...", "task_status": "PENDING" } }
```

### 查询任务

```
GET https://dashscope.aliyuncs.com/api/v1/tasks/{task_id}
Authorization: Bearer <apiKey>
```

返回 `output` 里带 `task_status`，成功时还有 `output_image_url`。

### 任务状态

| 状态 | 含义 | 要不要继续轮询 |
|---|---|---|
| `PENDING` | 排队中 | 是 |
| `RUNNING` | 处理中 | 是 |
| `SUSPENDED` | 挂起 | 是（但可能很久） |
| `SUCCEEDED` | 成功 | 停，取 `output_image_url` |
| `FAILED` | 失败 | 停，看 `code` / `message` |
| `UNKNOWN` | 任务不存在 | 停，多半是 `taskId` 传错 |

## 4. 扩图参数表

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `angle` | int | 0 | 逆时针旋转角度 [0, 359] |
| `output_ratio` | string | `""` | 宽高比：`""` / `1:1` / `3:4` / `4:3` / `9:16` / `16:9` |
| `x_scale` | float | 1.0 | 水平扩展比例 [1.0, 3.0] |
| `y_scale` | float | 1.0 | 垂直扩展比例 [1.0, 3.0] |
| `top_offset` | int | 0 | 上方加像素 |
| `bottom_offset` | int | 0 | 下方加像素 |
| `left_offset` | int | 0 | 左侧加像素 |
| `right_offset` | int | 0 | 右侧加像素 |
| `best_quality` | bool | false | 最佳质量，**耗时成倍增加** |
| `limit_image_size` | bool | true | 限制输出文件大小 |
| `add_watermark` | bool | **官方 true** | 加 "Generated by AI" 水印 |

注意 `add_watermark`：官方默认 `true`，笔记里设成 `false`。这是个**产品和合规**的取舍——去水印意味着用户可能把 AI 图当实拍图用。写代码时至少要知道自己关掉了什么。

## 5. 三套命名规则打架

这个功能里同时存在三套命名：

| 场合 | 规则 | 例子 |
|---|---|---|
| 阿里云 JSON | snake_case | `image_url` / `x_scale` |
| 前端传给我们 | camelCase | `imageUrl` / `xScale` |
| Java 字段 | camelCase | `imageUrl` / `xScale` |

**两套注解各管一条链路，不能混用**：

- `@Alias("image_url")` —— Hutool 的注解，管 **`JSONUtil.toJsonStr` 序列化**（我们发出去的 JSON）
- `@JsonProperty("xScale")` —— Jackson 的注解，管 **`@RequestBody` 反序列化**（前端传进来的 JSON）

Spring MVC 的 `@RequestBody` 用的是 Jackson，不是 Hutool。所以只加 `@Alias` 救不了入参；只加 `@JsonProperty` 救不了出参。

## 6. 实测：Jackson 的字段名推断规则

Lombok 给字段 `xScale` 生成 `getXScale()`。Jackson 拿到方法名后：

1. 去掉 `get` → `XScale`
2. 首字母小写 → `xScale`？
3. **不是**。Jackson 的 `legacyManglePropertyName` 规则是「连续大写全部转小写」，直到遇到第一个本来就是小写的字符。

所以 `XScale` 的处理过程是：

```
X → x     (大写，转小写，继续)
S → s     (还是大写，转小写，继续)
c → c     (本来就小写，停下，剩下的原样保留)
结果：xscale
```

### 实测数据

用一个不加任何注解的类 `{Float xScale; String imageUrl; String aValue;}`：

| 传进去的 JSON | 结果 |
|---|---|
| `{"xScale":1.5,"imageUrl":"u","aValue":"v"}` | `xScale=null`、`imageUrl=u`、`aValue=null` |
| `{"xscale":1.5,"imageUrl":"u","avalue":"v"}` | `xScale=1.5`、`imageUrl=u`、`aValue=v` |
| 反过来序列化 | `{"imageUrl":"u","avalue":null,"xscale":null}` |

### 关键结论

**只有「首字母小写 + 第二个字母大写」的字段会中招**：

- `imageUrl` ✅ 正常（第二个字母 `m` 是小写，第 1 步就停了）
- `xScale` ❌ → `xscale`
- `yScale` ❌ → `yscale`
- `aValue` / `iCount` / `uName` ❌ 同样中招

### 最危险的地方：不报错

如果 `FAIL_ON_UNKNOWN_PROPERTIES` 是 `true`，会抛：

```
UnrecognizedPropertyException: Unrecognized field "xScale" ...
(3 known properties: "avalue", "xscale", "imageUrl")
```

但 **Spring Boot 默认把它关掉了**（`Jackson2ObjectMapperBuilder` 里显式设为 `false`），所以真实接口里的表现是：

> 前端传 `xScale` → 字段静默为 null → 扩图用默认 1.0 → 用户觉得「扩图没效果」 → 而日志里一条错都没有。

**静默的错误比报错难查一百倍。**

## 7. 实测：Hutool 的双向行为

### 出参（序列化）：`@Alias` 有效

`JSONUtil.toJsonStr(request)` 实测产出 `image_url` / `x_scale` / `output_ratio` / `top_offset` / `add_watermark`，没有驼峰残留。

### 入参（反序列化）：不需要注解

`JSONUtil.toBean(aliYunJson, XxxResponse.class)` **能自动把 snake_case 填进驼峰字段**：

```
{"request_id":"req-1","output":{"task_id":"t-1","task_status":"PENDING"}}
  → requestId=req-1, taskId=t-1, taskStatus=PENDING
```

所以 `CreateOutPaintingTaskResponse` / `GetOutPaintingTaskResponse` 里的字段**一个 `@Alias` 都没加**，也能正常解析。这个行为写了一条测试钉住（`parsesSnakeCaseResponseFromAliYun`），哪天升级 Hutool 变了会先红。

**教训**：注解要不要加，不能靠「看起来应该要」，要靠跑一次看结果。

## 8. `@Value` 里的那个冒号

```java
@Value("${aliYunAi.apiKey}")     // 笔记写法
@Value("${aliYunAi.apiKey:}")    // 我的写法
```

区别：

| 写法 | 没配 key 时 |
|---|---|
| 无冒号 | **应用启动失败**：`IllegalArgumentException: Could not resolve placeholder 'aliYunAi.apiKey'` |
| 有冒号 | 正常启动，`apiKey = ""`，调用扩图接口时才抛「未配置阿里云 AI apiKey…」 |

选后者的理由：**配置缺失不应该让整个应用起不来**。扩图只是众多功能之一，为了它让登录、上传、空间全部不可用，是不划算的。

这是「快速失败」和「可用性」的取舍。反过来，如果是数据库密码这种「没有就什么也做不了」的配置，就该用无冒号版本，让它启动即失败。

## 9. 权限校验：为什么不能只判断「图片存在」

新增的 `checkPictureAuth` 分两条路：

```java
if (spaceId != null) {
    spacePermissionHelper.checkSpaceAccess(spaceId, loginUser);   // 空间图片：能进这个空间就行
    return;
}
if (!isAdmin && !本人) throw NO_AUTH_ERROR;                       // 公共图片：本人或管理员
```

**如果只判断 `picture != null` 会怎样？**

任何人都能拿一个 id 去调扩图接口。扩图**按次收费**，等于把你的额度开放给全互联网。而且这不是「数据泄露」级别的问题，是**直接的经济损失**，还不会有任何告警。

同类风险还有：拿别人的图去扩图，结果存到自己图库里 —— 变成了「用别人的素材生成新图」的洗稿工具。

**通用规律**：任何**有成本**的操作（调用付费 API、发短信、发邮件、跑模型），权限校验的严格程度要比只读接口高一档。

## 10. 超时与异常收敛

### 超时

```java
private static final int TIMEOUT_MILLIS = 10_000;
```

Hutool 的 `HttpRequest` **默认不限时**。不设超时，第三方卡住时你的线程会一直挂着 —— 这比报错严重得多，因为它不会触发任何告警，只会让线程池慢慢漏光。

### 异常收敛

```java
} catch (BusinessException e) {
    throw e;                        // 业务异常原样抛，保留错误码
} catch (Exception e) {
    throw new BusinessException(ErrorCode.OPERATION_ERROR, "...");   // 其他一律包成业务异常
}
```

两个理由：

1. **不能让 `HttpException` 直接冒到全局异常处理器**，否则前端拿到的是 500 + 一段堆栈，而不是 `{code, message}`。
2. **`BusinessException` 必须先 catch**，否则它会被 `catch (Exception)` 吞掉，错误码从 `NO_AUTH_ERROR` 变成 `OPERATION_ERROR`。

**catch 的顺序本身就是逻辑**，写反了不报错，但错误码会悄悄变。

## 11. 前端轮询该怎么做（给前端同学的说明）

轮询不是「死循环 + sleep」，至少要有三件事：

1. **间隔**：2~3 秒起步。扩图几十秒，1 秒一次纯属浪费。
2. **退避**：连续多次还是 `RUNNING`，就把间隔翻倍（3s → 6s → 12s），上限 10 秒。
3. **上限**：设一个总时长（比如 3 分钟），超了提示「任务超时，请到任务列表查看」，**而不是无限轮询**。

还要处理：
- 用户切走页面 → 停轮询（`visibilitychange`）
- 拿到 `SUCCEEDED` 后立刻停，别再多打一次
- `FAILED` 时把 `code` / `message` 展示出来，别只说「失败了」

## 12. 已知局限

| 局限 | 后果 | 要做的话 |
|---|---|---|
| 扩图结果**不入库** | 用户拿到 URL 后刷新页面就没了 | 前端拿到 URL 后走现有 `/picture/upload?fileUrl=` 保存，或后端加一个「保存到图库」接口 |
| 没有任务表 | 关掉页面就查不到自己发起过哪些任务 | 建 `picture_out_painting_task` 表，记录 `taskId` / `pictureId` / `userId` / 状态 |
| 没有幂等 | 连点 3 次 = 3 个任务 = 3 次扣费 | 前端按钮置灰 + 后端按 `(pictureId, userId)` 加短期锁 |
| apiKey 明文 | 泄露后额度被盗刷 | 走环境变量 / 配置中心，别提交进 git |
| 没有重试 | 阿里云偶发 5xx 直接失败 | 只对**创建任务**做有限重试（查询任务重试无害，创建任务重试会重复计费） |

最后一条值得单独记：**「能不能重试」取决于操作是否幂等**。查询任务天然幂等，随便重试；创建任务不幂等，重试就是重复下单。

## 13. 三条工程习惯

1. **「应该要加注解」不是理由，跑一次看结果才是。**
   这一章我先推导出 Jackson 的 `xscale` 问题，然后写探针实测确认；同样是「snake_case 转驼峰」，我以为 Hutool 反序列化也要加 `@Alias`，实测发现不用。两个方向都得测。

2. **静默失败比报错难查。**
   `xScale` 匹配不上不报错（Spring Boot 关了 `FAIL_ON_UNKNOWN_PROPERTIES`）；UPDATE 影响 0 行也不报错（上一章）。这类问题不会出现在日志里，只能靠「主动验证输入真的进去了」来发现。

3. **有成本的接口，权限要单独想一遍。**
   只读接口漏了权限是数据泄露；付费接口漏了权限是直接烧钱。两者的严重程度不一样。
