## 一、这段做了什么

### 1. 新增一张表 `space_user`

```sql
create table if not exists space_user
(
    id         bigint auto_increment comment 'id' primary key,
    spaceId    bigint                                 not null comment '空间 id',
    userId     bigint                                 not null comment '用户 id',
    spaceRole  varchar(128) default 'viewer'          null comment '空间角色：viewer/editor/admin',
    createTime datetime     default CURRENT_TIMESTAMP not null comment '创建时间',
    updateTime datetime     default CURRENT_TIMESTAMP not null on update CURRENT_TIMESTAMP comment '更新时间',
    UNIQUE KEY uk_spaceId_userId (spaceId, userId),
    INDEX idx_spaceId (spaceId),
    INDEX idx_userId (userId)
) comment '空间用户关联' collate = utf8mb4_unicode_ci;
```

### 2. 新增 6 个接口

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/spaceUser/add` | 把某个用户加进某个团队空间，指定角色 |
| POST | `/spaceUser/delete` | 把成员从空间移除 |
| POST | `/spaceUser/get` | 查某个用户在某空间的成员记录 |
| POST | `/spaceUser/list` | 查某空间的成员列表（带用户信息、空间信息） |
| POST | `/spaceUser/edit` | 改成员的角色 |
| POST | `/spaceUser/list/my` | 查"我加入的团队空间" |

### 3. 改造 `SpaceServiceImpl.createSpace`

原来只会建私有空间（`space.setSpaceType(PRIVATE)` 是硬编码的），现在：

- `spaceType` 为空 → 默认私有空间
- 普通用户按 `spaceType` 分别限 1 个（私有 1 个 + 团队 1 个），管理员不限
- **建团队空间时自动往 `space_user` 插一条 `admin` 记录**

## 二、为什么要有 `space_user` 这张表

空间和用户是**多对多**：

- 一个空间有多个成员
- 一个用户可以加入多个团队空间

多对多必须用关联表。能不能直接在 `space` 表加个 `memberIds` 字段存 JSON 数组？能跑，但：

1. 查"我加入了哪些空间"要全表扫 + 字符串匹配，索引失效
2. 改一个人的角色要读出整个数组再写回，**并发下丢更新**（第 10 章 `totalSize` 那个坑的同型问题）
3. 没法给"某人某空间"加唯一约束

**私有空间不需要成员概念**——私有空间只有创建者一个人。所以 `space_user` 里的记录只对应团队空间。但代码上不必额外判空，因为私有空间根本不会往里写记录。

## 三、表设计的三个决定

### 1. 有唯一键，就**不能**加逻辑删除

第 8 章给 `picture` 加了 `isDelete`，这里刻意不加，原因是：

```sql
UNIQUE KEY uk_spaceId_userId (spaceId, userId)
```

如果加了逻辑删除，用户 A 被移出空间（`isDelete=1`），再想加回来时会**撞唯一键**——因为那行还在，只是被"逻辑删"了。要么改成"先查再复活"（复杂），要么干脆物理删除。

所以这张表的删除是**真删**。业务上也没问题：成员关系没有"历史价值"，不像图片删了还要能找回。

> 一般规律：**有业务唯一约束的表，慎用逻辑删除**。要么唯一键里带上 `isDelete`（但 MySQL 下同一 `isDelete=1` 也只能有一行），要么就物理删。

### 2. `createTime` / `updateTime` 交给数据库默认值

实体里这两个字段是 `Date`，插入时是 `null`。因为第 8 章确认过 MP 的默认更新策略是 `NOT_NULL`——**null 字段不会出现在 SQL 里**，所以 INSERT 语句里没有这两列，数据库的 `DEFAULT CURRENT_TIMESTAMP` 和 `ON UPDATE CURRENT_TIMESTAMP` 就生效了。

如果哪天有人把策略改成 `ALWAYS`，这两列会以 `NULL` 插入，直接违反 `NOT NULL` 约束报错。

### 3. 三个索引各管一件事

- `uk_spaceId_userId`：唯一约束 + "查某人在某空间的记录"（最左前缀 `spaceId`）
- `idx_spaceId`：查某空间的成员列表（其实被唯一键的最左前缀覆盖了，属于冗余但无害）
- `idx_userId`：**查"我加入了哪些空间"**——这个必须有，否则 `/list/my` 要全表扫

## 四、创建团队空间 vs 创建私有空间

| 维度 | 私有空间 | 团队空间 |
|---|---|---|
| `spaceType` | 0 | 1 |
| 数量限制 | 每人 1 个 | 每人 1 个 |
| 成员表 | 不写 | **必须写一条创建人 = admin** |
| 谁有权限 | 只有创建者 | 创建者 + 所有成员（按角色） |
| 数据分表 | 不分 | 旗舰版可分（11-C，本次不做） |

**"必须自动写一条 admin 记录"是这段最关键的一行代码。** 不写会怎样？

- 空间建出来了，但创建人自己不在成员表里
- 后面所有"判断这个人是不是空间成员"的校验都会把他判成**外人**
- 结果就是：**用户创建了一个自己进不去的空间**，而且因为每人只能建 1 个团队空间，他连重建的机会都没有

这就是"**数据一致性的初始化**"——一个对象创建时，它的所有关联状态必须同时就位，否则会留下永远修不好的孤儿数据。

## 五、循环依赖：为什么会成环，怎么破

### 1. 环是怎么形成的

```
SpaceServiceImpl.createSpace()  ──需要──▶  SpaceUserService（插成员记录）
SpaceUserServiceImpl.validSpaceUser()  ──需要──▶  SpaceService（查空间是否存在）
```

`SpaceServiceImpl` 注入 `SpaceUserService`，`SpaceUserServiceImpl` 注入 `SpaceService`，**闭环**。

### 2. 为什么必须处理

Spring Boot **2.6 起默认禁止循环引用**（`spring.main.allow-circular-references=false`）。项目是 2.7.6，所以直接注入会启动失败：

```
The dependencies of some of the beans in the application context form a cycle
```

### 3. 三种解法对比

| 解法 | 做法 | 代价 |
|---|---|---|
| `@Lazy` | 在注入点加 `@Lazy`，Spring 注入一个延迟代理 | 环还在，只是被推迟；调试时调用链多一层，容易出 `BeanCurrentlyInCreationException` |
| **直接用 Mapper**（本项目选这个） | `SpaceServiceImpl` 注入 `SpaceUserMapper`，不走 Service | 绕开业务层，但这条插入是纯 insert，不需要任何校验 |
| 事件解耦 | 发布 `SpaceCreatedEvent`，由监听器插成员 | 最终一致（异步默认），建完空间到成员记录落库之间有窗口期 |

选 Mapper 的判断依据是：**要复用的是"一条 insert"，不是"一套业务规则"**。`addSpaceUser` 里有"用户不存在""空间不存在""角色合法""不能重复"四条校验，而这里四条全都已知（创建人刚登录、空间刚插入、角色固定 admin、必然不重复）。为了用不上的校验去制造一个环，不值。

顺带一提：`@Lazy` 也能让项目跑起来，但它把"设计问题"变成了"运行时依赖注入技巧"，后面接手的人看不懂为什么这里要 `@Lazy`。

## 六、`addSpaceUser` 的校验顺序

```java
1. 请求体非空                     → PARAMS_ERROR
2. validSpaceUser(spaceUser, true)
   ├─ spaceId / userId 非空        → PARAMS_ERROR「空间 id 和用户 id 不能为空」
   ├─ userId 对应的用户存在         → NOT_FOUND_ERROR「用户不存在」
   ├─ spaceId 对应的空间存在        → NOT_FOUND_ERROR「空间不存在」
   └─ spaceRole 合法（null 放行）   → PARAMS_ERROR「空间角色不存在」
3. 查重：该 (spaceId, userId) 已存在 → OPERATION_ERROR「该用户已在该空间中」
4. spaceRole 为空 → 默认 viewer
5. save
```

**为什么先查重再插入，而不是直接插、靠唯一索引报错？**

唯一索引确实能兜住，但抛出来的是 `DuplicateKeyException`，会被全局异常处理器翻译成 500「系统错误」——用户看到的是"服务器挂了"，而不是"这个人已经在空间里了"。

先查一次是为了**可读的错误信息**；唯一索引是**并发下的最后一道防线**。

### 这里有个 TOCTOU 窗口

```
线程 A: count → 0
线程 B: count → 0        ← 两个都通过了查重
线程 A: insert OK
线程 B: insert → DuplicateKeyException → 500
```

`count` 和 `insert` 之间不是原子的。两个请求同时把同一个人加进同一个空间，第二个会拿到 500。

**唯一索引在这里不是可选项，是正确性的保证**：没有它，就会产生两条重复的成员记录。有它，最坏情况是"错误信息不友好"，而不是"数据错了"。

彻底解决要么加分布式锁，要么把 `DuplicateKeyException` 也翻译成友好提示。笔记没做，我们也没做，属于已知局限。

## 七、N+1 与批量回填

成员列表要返回"成员 + 用户昵称头像 + 空间名"。两种写法：

```java
// 写法 A：单条转换，循环调用 —— 100 个成员 = 201 次查询
for (SpaceUser su : list) {
    voList.add(getSpaceUserVO(su));   // 每次 getById(user) + getById(space)
}

// 写法 B：批量回填（本项目采用的）
Set<Long> userIds  = ...;            // 100 个成员可能只有 20 个不同用户
Set<Long> spaceIds = ...;            // 通常只有 1 个
Map<Long, User>  userMap  = userService.listByIds(userIds)  → 1 次
Map<Long, Space> spaceMap = spaceService.listByIds(spaceIds) → 1 次
```

**写法是 201 次查询，实际只要 2 次。** 这就是 N+1 问题——单看每一行代码都没错，错在"在循环里"。

两个细节：

1. `Collectors.toMap` 必须带合并函数 `(a, b) -> a`，否则 `listByIds` 万一返回重复 id 会抛 `IllegalStateException: Duplicate key`。
2. `getSpaceUserVO`（单条版）仍然保留，因为 `/get` 接口只需要一条记录，用批量版反而多此一举。

## 八、角色 → 权限的映射

```java
VIEWER  = picture:view
EDITOR  = picture:view + picture:upload + picture:edit + picture:delete
ADMIN   = spaceUser:manage + 以上全部
```

这段只是把映射**定义好**，还没有任何地方**用它**。真正用起来是 11-B 的事：

- 每个接口上标 `@SaCheckPermission("picture:upload")` 之类的注解
- 登录时把"我在这个空间是什么角色"换算成权限列表，交给 Sa-Token 存起来
- 调用时 Sa-Token 拦一道，权限不够直接拒

**角色是给人看的，权限是给代码看的。** 中间隔一层映射的好处是：以后加一个"只能上传不能删"的新角色，不用改任何业务代码，只要在枚举里加一行。

## 九、本段故意留下的洞

这段的接口**一个权限校验都没有**，注释里写明了留给 Sa-Token 阶段。当前状态：

| 洞 | 后果 |
|---|---|
| `/spaceUser/add` 不校验调用者身份 | 任何人可以把**自己**加进任何人的团队空间，拿到编辑权限 |
| `/spaceUser/delete` 不校验 | 任何登录用户能踢掉任意空间的任意成员 |
| `/spaceUser/edit` 不校验 | 任何人能把自己的角色改成 admin |
| `/spaceUser/list` 不校验 | 传个 `spaceId` 就能看到该空间所有成员的用户信息（信息泄露） |
| `/spaceUser/list/my` 只按 userId 查 | 返回的空间里可能包含已被禁用的空间 |

这不是疏忽，是**先把功能跑通，再加横切关注点**的顺序。但如果这是真实项目而不是教学项目，这个中间状态**绝不能上线**。

## 十、已知局限

1. **移除成员是物理删除**，没有操作审计（谁踢了谁、什么时候踢的，查不到）
2. **添加成员没有"邀请"环节**：直接把别人拉进空间，对方没有同意/拒绝的机会，也没有通知
3. **没有分页**：`/spaceUser/list` 一次返回全部成员，成员上千时会撑爆响应
4. **重复添加的并发窗口**会返回 500（见第六节）
5. **`/list/my` 没有过滤已禁用/已删除的空间**
6. **角色只有三档**，做不到"这个成员只能看某个分类"

## 十一、三条工程习惯

1. **对象创建时的关联初始化要一次做全。** 建团队空间不写 admin 记录 = 造出一个自己都进不去的空间，而且用户没机会重来。凡是"创建 A 的同时必须创建 B"的地方，都要问一句：B 失败了，A 会回滚吗？（本项目在同一个 `@Transactional` 里，会。）
2. **唯一索引不是可选项，是并发正确性的最后一道防线。** 先查再插只是为了错误信息友好，别把它当成防重复的手段。
3. **循环依赖先问"我要复用的是什么"。** 复用业务规则 → 拆接口/提服务；复用一条 SQL → 直接用 Mapper。别一上来就 `@Lazy`。

## 十三、验收复盘（7 题）

这轮 7 题里 Q1 / Q3 / Q4 全对，Q2 / Q5 / Q6 / Q7 半懂。把四个补充点记在这里。

### 1. 为什么成员记录失败必须回滚：不可自愈的脏数据

额度不是独立的计数器，是**查表数出来的**：

```java
spaceService.count(new QueryWrapper<Space>()
        .eq("userId", loginUser.getId())
        .eq("spaceType", space.getSpaceType())) > 0
```

所以「空间 insert 成功、成员 insert 失败但没回滚」会留下这样的状态：

- 库里有他的 `spaceType=1` 空间
- 他不在 `space_user` 里 → 进不去
- 计数已经 = 1 → 再建报「每个用户每类空间仅能创建一个」

**这个用户被永久锁死了**，只能找 DBA 手删数据。失败可以重试，脏数据不能 —— 这是「关联初始化必须原子」的真正理由。

> 补一个容易被搞混的点：当前 `checkSpaceAccess` 判的是 `space.userId == loginUser.id`，所以**现在**创建人仍然删得掉自己的空间。要等 11-B 把团队空间改成按成员关系判权，他才会真的既进不去也删不掉。

### 2. N+1 的准确数字：去重是常被忽略的一半

100 个成员、来自 20 个不同用户：

| 写法 | 查询次数 |
|---|---|
| 循环调 `getSpaceUserVO` | 100 次 user + 100 次 space = **200**（+1 次列表 = 201） |
| `getSpaceUserVOList` | 1 次 `listByIds(user)` + 1 次 `listByIds(space)` = **2**（+1 = 3） |

注意单条版是 **100 次用户查询，不是 20 次** —— 它不去重。批量版先 `Collectors.toSet()` 去重成 20 个 id 再查一次。**去重和批量是 N+1 优化的两半，只做批量不做去重，最坏情况下省的并不多。**

### 3. 查重 与 唯一索引：一个管体验，一个管正确

| | 先 `count` 查重 | 唯一索引 `uk_spaceId_userId` |
|---|---|---|
| 作用 | 错误信息友好（「该用户已在该空间中」） | 并发下保证不产生重复行 |
| 只有它 | 并发时两个请求都通过 → 两条重复记录（数据错） | 直接报 `DuplicateKeyException` → 全局异常翻译成 500「系统错误」（体验差） |

两者分工不同，缺一不可。要再进一步，得把 `DuplicateKeyException` 也翻译成友好提示，或加分布式锁。

顺带抠个措辞：唯一键约束的是「**同一个人 + 同一个空间**只能有一条」，不是「一个人只能加一个空间」——一个人可以加很多个空间。

### 4. 功能权限 vs 数据权限

这是 Q7「加一个只能看某分类的角色」暴露出来的核心区分：

| | 功能权限 | 数据权限 |
|---|---|---|
| 管什么 | 能不能调用这个接口 | 能看到哪些**行** |
| 例子 | 有没有 `picture:view` | 只能看 `category='风景'` 的图 |
| 实现层 | Sa-Token 注解，接口入口拦一道 | 查询条件 / MyBatis 拦截器，落到 SQL 的 WHERE |
| 表达能力 | 动作级（view/upload/edit/delete） | 行级（按分类、按创建人、按空间） |

「只看某个分类」本质是**行级数据权限**，用功能权限键去表达有两条路：

- **路线 A**：把权限键升级成 `picture:view:category:风景` —— 分类是用户自建的动态数据，枚举里写死跟不上，会爆炸
- **路线 B**：接口层仍判 `picture:view`，在查询图片的 SQL 里加 `AND category IN (他有权看的分类)`

真实项目通常**两层都要**：接口层拦住没权限的人，查询层再按数据范围过滤。指望一个注解解决所有越权，是这一章最容易犯的错。

### 5. 这轮暴露的接口漏洞清单（11-B 要逐个堵）

| 接口 | 攻击者能做什么 |
|---|---|
| `/spaceUser/add` | 把**自己**加进别人的团队空间，角色随便填 → 直接拿到 admin |
| `/spaceUser/edit` | 把自己的角色改成 `admin` |
| `/spaceUser/delete` | 把空间的真管理员踢出去 |
| `/spaceUser/list` | 传任意 `spaceId` 就返回全部成员的 userId、昵称、头像 → 信息泄露 |
